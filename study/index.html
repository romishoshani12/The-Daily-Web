מה זה אתר בכלל? הדפדפן והשרת

מה זה MVC, ולמה מחלקים ככה

MVC הוא שם לדרך של לסדר את הקוד לשלוש ערימות, כך שלכל חלק יש תפקיד אחד.

שלוש האותיות

אותשםבשפה פשוטהבפרויקט
MModel (מודל)איך המידע נראה ואיפה הוא נשמר. לדוגמה: "לכתבה יש כותרת עד 180 תווים, תקציר, גוף, קטגוריה מתוך רשימה, וכותב".models/Article.js, ‏models/User.js…
VView (תצוגה)איך המידע נראה למשתמש. התבנית שהופכת לדף HTML.views/article.ejs, ‏views/write.ejs…
CController (בקר)המנהל: מקבל בקשה, מבקש מהמודל את המידע, ומחליט מה להחזיר: דף (View) או נתונים (JSON).controllers/article.js, ‏controllers/reporter.js…

למה לחלק? אם מחר רוצים לשנות את עיצוב דף הכתבה, נוגעים רק ב-View. אם רוצים להוסיף שדה לכתבה, נוגעים במודל. כל אחד בצוות יכול לעבוד על חלק אחר בלי להפריע לאחרים, וקל למצוא איפה כל דבר נמצא.

דוגמה אמיתית: פתיחת דף כתבה

  1. אתה נכנס לכתובת /articles/123.
  2. Route (routes/article.js:5): "כתובת שמתחילה ב-/articles/ הולכת לפונקציה article בבקר".
  3. Controller (controllers/article.js): "תביא מהמודל את כתבה 123, אבל רק אם היא פורסמה".
  4. Model (Article): שולף את הכתבה מ-MongoDB ומחזיר אותה.
  5. Controller: סופר צפייה (services/views.js), ואומר "תציג את התבנית article עם הכתבה הזו".
  6. View (views/article.ejs): ממלא את החורים (כותרת, גוף, תאריך) ויוצר דף HTML מלא.
  7. הדף חוזר לדפדפן, והדפדפן מציג אותו.
flowchart LR
  U[Browser: /articles/123] --> R[Route: routes/article.js]
  R --> C[Controller: controllers/article.js]
  C --> M[Model: models/Article.js]
  M --> DB[(MongoDB)]
  DB --> M
  M --> C
  C --> V[View: views/article.ejs]
  V --> U2[HTML page back to browser]

מה יש אצלנו מעבר ל-MVC

  • Routes: לוח השילוט שאומר לאיזה בקר הולכת כל כתובת.
  • Services: "ספר הכללים". למשל הכלל "רק כתבה במצב טיוטה אפשר להגיש" נמצא ב-services/submit.js (קובץ שאתה כתבת, קומיט 043). מוציאים כללים מהבקר כדי שאפשר יהיה לבדוק אותם לבד ולהשתמש בהם בכמה מקומות.
  • Middleware: בדיקות שרצות על כל בקשה לפני שהיא מגיעה לבקר. השומר בדלת.
  • Client JS (public/js): הקוד שרץ בדפדפן ומדבר עם השרת בלי לרענן את הדף.
משפט לבחינה: "השתמשנו ב-MVC: המודלים ב-Mongoose מגדירים את המבנה, ה-Views הם תבניות EJS שהשרת ממלא, והבקרים מחברים ביניהם. הוספנו שכבת Services ללוגיקה העסקית, ו-Middleware לאבטחה, כדי שהבקרים יישארו קצרים וברורים."

איך "מקשרים" בין מגירות

הכתבה לא מעתיקה לתוכה את כל פרטי הכותב. היא שומרת רק את מספר הזיהוי שלו בשדה author. כשצריך את השם, Mongoose הולך למגירת users ומביא אותו (זה נקרא populate). אותו דבר קורה בתגובה, שזוכרת את article, וברשומת צפייה, שזוכרת את article.

למה ככה? אם רועי משנה את השם שלו, משנים במקום אחד בלבד, וכל הכתבות שלו מציגות את השם החדש.

הכתובת

  • MongoDB רץ על המחשב שלך, בתוך קופסת Docker בשם daily-web-mongo (גרסה mongo:7).
  • הכתובת שלו נמצאת בקובץ .env בתיקיית הפרויקט:

    • 127.0.0.1: "המחשב הזה", כלומר לא שרת באינטרנט.

הסיפור המלא: איך מילה שהקלדת נשמרת במסד

זה הקוד שאתה כתבת (פיצ׳ר הכתב). כדאי לדעת לספר אותו כמו סיפור.

  1. אתה מקליד בתיבת "תוכן הכתבה" בדף /write/….
  2. הדפדפן שם לב: בקובץ public/js/write.js יש "מאזין" שמופעל בכל הקלדה. הוא רושם לעצמו "יש שינוי שלא נשמר" (dirty = true) ומפעיל את פונקציית השמירה pump().
  3. אוספים את הטופס: כותרת, תקציר, קטגוריה, תמונה וגוף נארזים לחבילת טקסט בפורמט JSON. מצרפים גם את מספר הגרסה שהדפדפן מכיר (revision).
  4. שולחים לשרת: בקשה מסוג PATCH (שפירושו "עדכון") לכתובת /api/work/articles/<מספר הכתבה>. מצרפים גם "סיסמת דף" (CSRF) שמוכיחה שהבקשה באה מהאתר שלנו. על המסך מופיע "שומרים את השינויים…".
  5. השומר בדלת (middleware/security.js): בודק את עוגיית הכניסה שלך ומוצא במסד את הסשן, ולכן יודע שאתה roy. בודק גם את סיסמת הדף.
  6. המלצר (routes/reporter.js:13): "PATCH לכתבה הולך לפונקציה save, אבל רק אם אתה כתב או עורך".
  7. הטבח (controllers/reporter.js, פונקציה save):
    • האם הכתבה קיימת, והאם היא שלך? (owned)
    • האם מותר לערוך אותה עכשיו, או שהיא ממתינה לעורך? (canEdit)
    • האם מספר הגרסה שלך עדכני? אם לא, מישהו שמר בינתיים, ומוחזרת שגיאה "רעננו את העמוד".
    • האם השדות תקינים (אורך, קטגוריה, כתובת תמונה)? (services/validation.js)
  8. המזווה: ‏Mongoose שולח ל-MongoDB פקודה אחת: "במגירת articles, מצא את הכתבה הזו רק אם הגרסה שלה עדיין X, החלף את הטיוטה בחדשה, והעלה את הגרסה ב-1". זה קורה בבת אחת, כך שאי אפשר שמישהו "ייכנס באמצע".

למה אין try/catch בבקרים?

בקרים כמו controllers/reporter.js הם async וזורקים שגיאות דרך fail(message, status) מתוך services/validation.js:2. ‏Express 5 תופס לבד Promise שנדחה ומעביר אותו למטפל השגיאות. ב-Express 4 זה היה דורש try/catch או עטיפה בכל handler.

function fail(message, status = 400) {
  const error = new Error(message); error.status = status; throw error;
}

ב. מחזור החיים של כתבה

  draft --> pending: submit (owner / editor)
  returned --> pending: submit again
  pending --> published: review publish (editor)
  pending --> returned: review return + note (editor)
  published --> draft: PATCH save (new draft cycle, published kept)
  1. יצירה: הכתב לוחץ "＋ כתבה חדשה" ב-/reporter. הכפתור ננעל, נשלח POST /api/work/articles, ונוצרת Article.create({author: req.user._id}) עם טיוטה ריקה ומצב draft. אחר כך מתבצעת הפניה ל-/write/:id (workspace.js:38-42).

  3. שמירה אוטומטית (write.js:12-35):
    • כל אירוע input מסמן dirty = true וקורא ל-pump().
    • pump() מריץ לולאה אחת בלבד: אם כבר יש שמירה בדרך (running), הקריאה מחזירה את אותה הבטחה. כך הבקשות נשלחות בזו אחר זו, ותשובה ישנה לא יכולה לדרוס חדשה.
    • לפני כל שליחה הלולאה משווה את הנתונים ל-lastSaved, ולא שולחת אם לא השתנה דבר.
    • הבקשה היא PATCH עם {...fields, revision}, והתשובה מחזירה revision חדש שהלקוח שומר.
    • חיווי למשתמש: "שומרים את השינויים…", ואז "✓ נשמר ב־HH:MM:SS".

    • owned ו-canEdit: כתב לא יכול לערוך כתבה ב-pending, ומקבל 409.
    • אם ה-revision לא תואם: 409 "יש גרסה חדשה יותר".
    • content(req.body) במצב לא מלא, כלומר שדות ריקים מותרים בטיוטה.
    • findOneAndUpdate אטומי. אם המצב היה published, הוא חוזר ל-draft, ו-published נשאר כמו שהוא.

דילמות והחלטות ארכיטקטוניות

שבע החלטות שעולות מהקוד. לכל אחת: הבעיה, האפשרות שנדחתה, הפתרון שנבחר והמחיר שלו.

בשפה פשוטה: דילמה היא שאלה של "למה עשיתם ככה ולא אחרת?". לכל בחירה יש בעיה שהיא פותרת ומחיר שמשלמים עליה. בתשובה טובה אומרים את שלושתם: מה הבעיה, מה בחרנו, ומה המחיר.

1. ‏draft ו-published נפרדים, במקום status בלבד

הבעיה: כתב עורך כתבה שכבר פורסמה, והקוראים לא אמורים לראות את השינויים עד שהעורך מאשר.

שנדחה: שדה תוכן אחד עם status. ברגע שהכתב מקליד, הציבור רואה את השינוי, ובזמן pending הכתבה הייתה נעלמת מהפיד.

נבחר: שני עותקים. הפיד מסנן לפי published: {$ne: null} ומציג רק את published.*. אישור מעתיק את draft ל-published (review.js:7).

המחיר: כפל אחסון של התוכן, ושאילתות שצריכות לבחור את העותק הנכון. במסכי הצוות זה draft.title, ובפיד זה published.title.

2. סשן ב-MongoDB עם hash של הטוקן, במקום זיכרון השרת או JWT

הבעיה: הדרישה היא שמשתמש יישאר מחובר אחרי restart של השרת, ושאפשר יהיה לבטל סשן.

שנדחה: סשן בזיכרון נמחק ב-restart. ‏JWT אי אפשר לבטל לפני שהוא פג.

נבחר: טוקן אקראי של 32 בתים בעוגיית HttpOnly + SameSite=strict, ובמסד נשמר רק sha256(token). מי שגונב את המסד לא יכול להתחבר עם מה שמצא בו. ‏TTL מוחק סשנים שפגו, ושינוי סיסמה מוחק את כל הסשנים של המשתמש (admin.js:27).

המחיר: שאילתה למסד בכל בקשה (identify).

3. ‏revision: מניעת דריסה (optimistic concurrency)

הבעיה: שני טאבים או שני מכשירים עורכים את אותה טיוטה, או שהעורך משנה סטטוס בזמן שהכתב מקליד.

שנדחה: last-write-wins, שדורס עבודה בשקט, או נעילה (lock), שמסובכת ונתקעת אם מישהו סוגר את הדפדפן.

נבחר: הלקוח שולח את ה-revision שהוא מכיר. העדכון מתבצע רק אם {revision, status} לא השתנו, ו-$inc מקדם את הגרסה באותה פעולה אטומית. אחרת מוחזר 409 "רעננו את העמוד".

המחיר: המשתמש השני צריך לרענן ולאבד את הקלט שלא נשמר. אין מיזוג אוטומטי.

4. תור שמירות סדרתי (pump), במקום debounce או בקשות מקבילות

הבעיה: שתי בקשות PATCH במקביל יכולות להגיע לשרת בסדר הפוך, והגרסה הישנה תדרוס את החדשה. בנוסף, השנייה תיכשל על revision.

נבחר: בקשה אחת בכל רגע. הקלדה בזמן שמירה רק מסמנת dirty, והלולאה שולחת את המצב העדכני מיד אחרי שהבקשה הקודמת חוזרת. כל בקשה נושאת את ה-revision שהתקבל בתשובה הקודמת.

המחיר: בהקלדה מהירה תמיד יש בקשה אחת "בדרך". ההחלטה הייתה לשמור מיד ולא לחכות ל-debounce, כדי שיהיה פחות סיכון לאבד טקסט.

5. סל צפיות שעתי (ViewStat), במקום מסמך לכל צפייה

הבעיה: צריך גרף צפיות לפי שעה ומונה כולל, בהיקף גדול.

שנדחה: מסמך לכל ביקור. מיליוני מסמכים, ואגרגציה כבדה בכל טעינת גרף.

נבחר: מסמך אחד לכל כתבה לכל שעה UTC, עם $inc ו-upsert ואינדקס ייחודי {article, hour}. אם שני ביקורים ראשונים באותה שעה יוצרים מסמך במקביל, אחד מקבל 11000 ומבצע ניסיון חוזר (views.js:7-11). השדה Article.views שומר את הסכום, כך שמיון "הכי נקראים" לא דורש אגרגציה.

המחיר: רזולוציה של שעה בלבד, ואין מידע על כל ביקור בנפרד. כל GET נספר, כולל רענונים ובוטים.

6. ‏Rate limit אטומי ב-MongoDB, במקום מונה בזיכרון

הבעיה: "3 תגובות בדקה מאותו מכשיר", גם כשבקשות מגיעות בדיוק באותו רגע.

שנדחה: מונה בזיכרון נעלם ב-restart ולא עובד עם כמה תהליכים. "קרא ואז כתוב" יוצר race condition, ושש בקשות מקבילות היו עוברות כולן.

נבחר: ‏findOneAndUpdate עם התנאי $expr: size(recent) < max ו-pipeline update שמסנן ניסיונות ישנים ומוסיף את הנוכחי, הכל באותה פעולה אטומית (rate-limit.js:9-11). זה חלון זמן נע (sliding window). בבדיקת הקבלה, מתוך 6 בקשות מקבילות 3 מתקבלות ו-3 נדחות עם 429.

המחיר: המפתח הוא עוגיית ה-visitor, כך שמחיקת עוגיות עוקפת את ההגבלה. בהתחברות המפתח הוא IP מגובב.

7. ‏Offset בפיד, cursor בתגובות

פיד: ‏skip/limit עם page. זה פשוט, תומך במיון לפי צפיות, ונותן count לתצוגה. כדי שעמודים לא יחפפו יש _id לשבירת שוויון.

תגובות: cursor ‏before=createdAt_id. אם עורך מוחק תגובה מוקדמת, offset היה מזיז את כל הרשימה ומדלג על תגובה. cursor מתחיל בדיוק אחרי הפריט האחרון שהוצג. ‏limit(21) אומר אם יש עוד, בלי countDocuments.

המחיר: ‏skip בעמודים עמוקים מאט, כי MongoDB סורק ומדלג. זו מגבלה ידועה בעומס גבוה.

עוד החלטות קצרות

  • SSR לדף כתבה: התוכן נמצא ב-View Source (דרישה), עובד בלי JS וטוב ל-SEO. ‏<%= %> מבצע escape, כך שתגית שכתב מקליד לא תרוץ.
  • מזג אוויר דרך השרת: ה-CSP מתיר connect-src 'self' בלבד. השרת שומר cache, מאחד בקשות (pending), מגביל ל-15 דקות לפי זמן התצפית של הספק ומשהה ניסיונות ל-30 שניות אחרי כשל. אם אין נתון טרי מוחזר 503, ולא נתון ישן.
  • השבתה במקום מחיקה: משתמש עם כתבות לא נמחק (409), כדי לא לאבד את שיוך הכתבות.
  • הרשאה בשרת ולא רק הסתרת כפתורים: כל API בודק requireRole ו-owned. אפשר לשלוח בקשה ידנית מ-DevTools ולקבל 403.

מגבלות ידועות: מה היית משפר

  • מחיקת כתבה עם תגובות ונתוני צפייה, ותיקון רשומת צפייה, הן כמה פעולות נפרדות בלי transaction.
  • אין זיהוי של ביקורים חוזרים או בוטים בספירת הצפיות.
  • skip בעמודים עמוקים, ו-$regex בלי אינדקס טקסט, יאטו כשיהיו הרבה נתונים.
  • אין מיזוג טיוטות כשיש 409, רק בקשה לרענן.
  • אין הגבלת קצב על יצירת כתבות או על שמירה אוטומטית.
